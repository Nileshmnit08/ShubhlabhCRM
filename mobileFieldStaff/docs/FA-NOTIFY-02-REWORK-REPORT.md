# FA-NOTIFY-02-REWORK: Zero-Cost Android System Push Notifications

## 1. Executive Summary
The Android System Push Notifications feature has been fully reworked. The previously proposed Firebase/FCM integration has been **COMPLETELY REMOVED** and the system now strictly adheres to the ZERO-COST requirement. It leverages existing Supabase Realtime subscriptions and local Android notifications using `expo-notifications`, complemented by `expo-background-fetch` to provide a conservative background fallback for missed notifications.

## 2. Existing Notification Architecture Audit
The audit confirmed:
- `crm_notifications` table is the single source of truth.
- `NotificationRouter.js` perfectly handles deep-linking based on `entity_id` (`conversation_id`).
- `NotificationContext.js` actively listens to Supabase Realtime.
- The previous implementation attempted to bypass this with an expensive/complex FCM integration which was against requirements.

## 3. Firebase/FCM Removal
- All references to FCM, `googleServicesFile`, the `device_push_tokens` migration, the Supabase Edge Function `send-fcm-notification`, and the `PushTokenService.js` were completely deleted from the codebase.
- Verified that `package.json` contains no Firebase dependencies.

## 4. Final Notification Architecture
1. **Foreground/Active State**: Supabase Realtime detects a new `crm_notifications` insert.
2. **Foreground/Active State UX**: If the user is viewing the same chat, it's silently marked as read. If not, `Notifications.scheduleNotificationAsync()` fires a real Android system notification instead of an in-app overlay toast.
3. **Background State (Alive)**: If Android hasn't killed the WebSocket yet, the Realtime listener will still fire the local notification.
4. **Terminated/Deep Background State**: A scheduled Expo Task (`BACKGROUND_NOTIFICATION_TASK`) periodically wakes up to fetch unread `crm_notifications` and generate local notifications.

## 5. Local Android Notification Implementation
- Integrated `expo-notifications` strictly for local notifications (no push tokens generated).
- Created a `chat_messages` Android notification channel with `AndroidImportance.MAX`.
- Replaced the fake WhatsApp-style in-app toast for chat messages with real Android system notifications.

## 6. Supabase Realtime Integration
- The existing Realtime subscription in `NotificationContext.js` remains the primary driver. We simply changed its side-effect from `showToast()` to `Notifications.scheduleNotificationAsync()`.

## 7. Background Checking Approach
- Integrated `expo-background-fetch` and `expo-task-manager`.
- Created `BackgroundNotificationService.js` to register `BACKGROUND_NOTIFICATION_TASK` with a minimum interval of 15 minutes.
- The task queries `crm_notifications` for unread messages newer than `@last_bg_check_${userId}` and fires local notifications.

## 8. Exact Chat Deep-Link Architecture
- Tapping the local notification triggers `Notifications.addNotificationResponseReceivedListener`.
- The listener extracts the payload and maps it into a pseudo `crm_notifications` object.
- It then calls the existing `handleNotificationPress()` function.

## 9. conversation_id Routing
- The notification payload generated by the app contains `conversation_id`.
- `handleNotificationPress` correctly maps this to `navigate('ChatConversation', { conversationId })`.

## 10. Duplicate Prevention
- Notifications are only fired if `is_read = false`.
- If the user is actively viewing the `activeChatId`, the system notification is suppressed.
- Background tasks query based on `lastCheckTime` stored in `AsyncStorage`.

## 11. Permission Handling
- `App.js` requests `POST_NOTIFICATIONS` permission immediately upon startup.

## 12. Security/RLS
- Background fetches use `supabase.auth.getSession()` to ensure they only fetch notifications for the authenticated user.
- No server-side secrets or bypassing of RLS is used.

## 19. Background/Terminated App Limitations
- **Instant remote delivery to a fully terminated app is impossible without FCM.**
- The application relies on `expo-background-fetch` when fully terminated. This is restricted by Android's Doze mode and JobScheduler, which enforces a minimum of ~15-minute intervals and may suspend it entirely to save battery.
- Therefore, notifications received while the app is completely dead will be delayed until the next background fetch window or until the user re-opens the app.
