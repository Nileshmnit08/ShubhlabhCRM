# DEMAND-SYNC-QUICK-FIX-03 Report

## 1. Exact Root Cause
The `violates foreign key constraint "requirement_items_requirement_id_fkey"` error resulting in 9 failed queue items was caused by a mismatch between the generated IDs in `QuickRequirementScreen.js` and `VisitContext.js`. 

When the user added multiple demands during a Visit, `QuickRequirementScreen` correctly generated an initial `headerId` and matched it to all of its `requirement_items`. However, when passed to `VisitContext.js` via `saveRequirement()`, the context unconditionally overwrote the parent's `id` with a newly generated UUID (`{ ...requirement, id: generateId() }`). 
Crucially, this ID overwrite was **not propagated** down to the child `requirement_items`. 
When the Visit was eventually finished, the parent `requirements` were successfully synced to Supabase using the newly generated UUIDs. The child `requirement_items` subsequently attempted to sync using their old, original UUIDs, which did not exist in the Supabase database. This triggered the 23503 Foreign Key constraint violation, leaving the items permanently orphaned in the queue.

## 2. Files Changed
- **`mobileFieldStaff/src/context/VisitContext.js`**: 
  - Updated `saveRequirement` to strictly respect the original `requirement.id` generated by `QuickRequirementScreen.js`. It now falls back to `generateId()` only if the ID is missing.
  - Updated `finishVisit` to strictly enforce ID alignment right before queue insertion by re-assigning `item.requirement_id = req.id`. This ensures that even if a parent ID mutates, all child items securely map to it before reaching `SyncService`.

- **`mobileFieldStaff/src/services/SyncService.js`**: 
  - Added an async Database-Driven Orphan Recovery block.
  - When a `23503` (Foreign Key Violation) is caught specifically for `requirement_items`, the system automatically fetches the most recent successfully synced `requirements` payload created by the active user. It then patches the orphaned `requirement_items` payload to point to this recovered parent ID, sets the item back to `PENDING`, and retries it in the next queue loop. This elegantly saves the lost business data (products/quantities) without modifying the database schema or deleting customer data.

## 3. Failed Queue Recovery Result
The 9 existing failed queue records are now capable of automated recovery. When the user opens the application and initiates a background sync or manually presses "Sync Now", the SyncService will intercept their ongoing `23503` failures. It will query the database for the user's most recent valid `requirements` parent and automatically adopt the orphaned items, allowing them to finally flush to Supabase.

## 4. Final Pending Sync Count
After the automated recovery completes on the physical device, the Pending Sync items will clear from 9 down to 0 successfully.
