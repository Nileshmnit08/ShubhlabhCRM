# CHAT-MOBILE-05: Offline Inbox Architecture Report

## 1. Exact Root Cause of the Bug
The offline-generated conversation created via "Start Chat" was not appearing in the Inbox (All Messages screen). This occurred because `ChatService.getConversations()` strictly returned data from the online Supabase query or a static `@chat_conversations_{userId}` cache. However, the offline fallback generator inside `getOrCreateConversation()` did not append its newly minted conversation object into the local cache, effectively rendering the offline conversation invisible everywhere except local React state navigation params. Furthermore, pending offline messages from the `SyncService` queue were completely ignored by the Inbox, hiding the "latest message" preview.

## 2. Local Persistence Implementation
I updated `getOrCreateConversation` to accept the full `selectedStaff` object. When an offline conversation is triggered, the client creates a UUID and pushes a serialized object directly into the top of `@chat_conversations_{userId}` via `AsyncStorage`. This guarantees it acts as a fully persisted, durable entity before any network sync occurs. 

## 3. Inbox Merge Implementation
`getConversations()` now implements a three-tier deduplicated merge strategy:
1. Load all conversations from `AsyncStorage` (capturing any offline creations).
2. Fetch live data from Supabase and overwrite the local cache (resolving `pending` states to synced states).
3. Query `SyncService.getQueue()` for any `chat_messages` pending upload.
4. Merge them! The code injects the latest pending message into the conversation object, dynamically mutating `updated_at` and displaying a "clock" icon on the UI preview to reflect the `SyncService` state.

## 4. Conversation ID Mapping
No complex custom ID mapping tables were necessary! Because `chat_conversations.id` natively supports UUID v4 inserts provided by the client, the offline UUID generated by `ChatService` naturally becomes the authoritative ID across the entire lifecycle, eliminating ID-mapping edge cases.

## 5. Sync Behavior
The `SyncService` iterates cleanly:
1. `chat_conversations` (INSERT UUID)
2. `chat_participants` (INSERT Participant A)
3. `chat_participants` (INSERT Participant B)
4. `chat_messages` (INSERT text)

If the server already has the conversation, it bounces harmlessly against the primary key. Idempotency is structurally guaranteed.
